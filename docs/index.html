About

Maps built by different sensors — monocular cameras, RGB-D, LiDAR — describe the same environment in incompatible ways, and monocular maps additionally lack absolute scale. All three modalities, however, observe the same underlying 3D line structure. SCALAR registers 3D line maps across modalities by estimating the full Sim(3) transformation (scale + rotation + translation) from line geometry alone, with two components: ScalePluckerNet, a scale-invariant line matcher trained on fully synthetic, SLAM-calibrated Sim(3) data, and a line-based Sim(3) estimator that replaces the classical consensus vote — which we show is provably wrong on repetitive structure — with whole-map metric verification.

The visualization above shows a real registration from our benchmark: a monocular SLAM line map (unknown scale) aligned to an RGB-D reference map of the 7-Scenes heads scene by the shipped pipeline — 3.5° rotation error, 4% scale error, 2 cm translation error. The synthetic scenes illustrate the training distribution.

The problem

Under Sim(3), a Plücker line L = [m; d] transforms as d′ = Rd, m′ = s·Rm + t×d′. SE(3)-trained line matchers (PlückerNet, CVPR 2021) misread the residual (s−1)·Rm as translation and collapse under exactly the scale mismatch that cross-modal registration must resolve. On the estimation side, repetitive indoor and street structure makes consensus maximization itself unsound: wrong-but-mutually-consistent matches on repeating geometry outvote the true pose, so RANSAC — and even certifiably optimal consensus solvers — return a confidently flipped registration.

Two purpose-built answers: a matcher whose training data (not architecture) carries scale invariance and SLAM-realistic noise; and an estimator that proposes with closed-form solvers, keeps multiple rotation hypotheses alive, and disposes by scale-sensitive verification against the full maps.

Plücker Coordinates

A 3D line through point p with unit direction d is encoded as:

L = (m, d) m = p × d (moment vector)

Transformation Laws

GroupDirectionMoment
SE(3) (R, t)d′ = R dm′ = R m + t × R d
Sim(3) (s, R, t)d′ = R dm′ = s · R m + t × R d

Why the SE(3) Solver Fails

The SE(3) solver assumes m₂ = R m₁ + t × R d₁ and minimises the residual:

e = m₂ − R m₁ − t × R d₁ = (s − 1) · R m₁ for a Sim(3)-transformed pair

This residual is non-zero for any s ≠ 1 and cannot be made zero by any choice of t. It grows linearly with |s − 1| and with the magnitude of the moment vectors.

Consequences:

  • Rotation is unaffected — direction vectors are unit vectors, so d′ = Rd is scale-invariant. The SVD rotation step recovers R exactly.
  • Translation is badly biased — the solver absorbs (s−1)·Rm₁ into a spurious translation, giving wrong t and a meaningless pose estimate.

Method

The PluckerNetKnn architecture is unchanged — scale invariance comes entirely from the training data, and pose estimation is handled by a purpose-built line-based Sim(3) estimator (lib/sim3_solver.py, one self-contained file) rather than consensus-maximizing RANSAC.

The Sim(3) estimator in one paragraph

Both maps are pre-normalized so every threshold is scale-free. Rotation candidates come from batched 2-pair Procrustes hypotheses on matcher candidates plus a uniform SO(3) grid, scored under both a matcher-weighted objective and a correspondence-free direction-distribution objective — and the top ~14 peaks are all kept, because Manhattan-world flips dominate any direction-only score. Candidate correspondences are purified by a soft pairwise-consistency (PCM) filter; every surviving 2-pair combination yields a linear (t, s) solve in one batched pass, bounded by an extent-ratio scale prior. Every pose is then verified against the full maps with a combined moment + perpendicular residual score — the true arbiter that consensus counting cannot game. A re-proposal beam over the top rotation-distinct poses and one guarded least-squares refit finish the estimate, in ~0.3 s per map pair.

Why the network does not need to change for Sim(3): directions transform as d′ = Rd (scale-invariant), so the KNN graph structure is identical in both views. The GNN's cross-attention learns to match lines with the same rotated direction and consistent moment ratio. Scale is recovered analytically by RANSAC from the moment magnitudes of the matched pairs — the network never sees it explicitly.

Output: prob_matrix — soft doubly-stochastic matrix where prob_matrix[b,i,j] is the probability that line i in cloud 1 corresponds to line j in cloud 2.

Plücker Line Format

All Sim(3) code uses [m, d] order — moment first, direction last:

L = [m₀ m₁ m₂ d₀ d₁ d₂] m = p × d (moment), d = unit direction

The original SE(3) PlueckerNet uses [d, m] order. Conversion is handled by scripts/convert_se3_datasets.py. The 9D color extension appends LAB: [m₀,m₁,m₂, d₀,d₁,d₂, L*,A*,B*].

Minimal Solver — 2 line pairs

Given R from direction SVD (scale-invariant), each line contributes one moment equation:

s·Rm₁ᵢ − [d₂ᵢ×]·t = m₂ᵢ Stack 2 pairs → 6 equations, 4 unknowns [s, t]: ⎡ Rm₁₁ −skew(d₂₁) ⎤ ⎡ s ⎤ ⎡ m₂₁ ⎤ ⎢ ⎥ ⎢ ⎥ = ⎢ ⎥ → x = lstsq(A, b) ⎣ Rm₁₂ −skew(d₂₂) ⎦ ⎣ t ⎦ ⎣ m₂₂ ⎦ Hypotheses with s ≤ 0 are rejected. Inlier criterion: ‖L₂ − M_sim3·L₁‖₂ < τ where M_sim3 = [ s·R [t×]·R ] [ 0 R ] Best hypothesis refined on all inliers via overdetermined least squares.

Training Objective

Binary cross-entropy loss on the predicted prob_matrix vs the ground-truth match matrix C_gt:

L = −( C_gt · log(P + ε) + (1 − C_gt) · log(1 − P + ε) ).mean()

RANSAC is not used during training — only called during validation to report pose metrics. The training checkpoint is selected by recall_rot (fraction of scenes where Grassmannian RANSAC recovers rotation within 5°/10°/15°/20°).

Dataset Pipeline

Fully synthetic, calibrated against real SLAM maps. ScalePluckerNet never sees a real scene: scripts/generate_synthetic.py produces 200k train / 2k valid Plücker line-map pairs whose scale distribution, physical noise (Rayleigh direction + perpendicular foot-point perturbations that preserve m·d = 0), sign flips (~50%), fragmentation (1–3 query fragments per reference edge), and drift are all matched to measured statistics of real mono-vs-metric Structure-PLP-SLAM map pairs.

Eleven scenario families

ScenarioWhat it teaches
room / submap / relocalize / loop / dense-sparseeveryday indoor session pairs at varying overlap and density
manhattan3 orthogonal line families — the flip-ambiguity regime
corridor1–2 dominant directions, near-degenerate geometry
hard_noise5–20% inliers, drifty-run noise, confuser outliers
adversarialrepeating direction clusters — disambiguate by moment context
outdoorbuilding-scale facades (8–20 m)
street (v6)KITTI-calibrated street canyons: 1–3 chained ~90° segments, periodically repeating facades (the 180° flip alias), metric–metric scale s ≈ 1, clouds up to 2,200 lines, ~20% overlap concentrated on cross-modally shared verticals/curbs

Scale & noise calibration (v4 → v6)

  • Scale: log-normal around the measured mono-to-metric median (2.2), clipped to the observed GT range [0.4, 13]; street pairs are metric–metric (s ≈ 1)
  • Direction noise: Rayleigh σ = 5.2° → median ≈ 6.1° — identical to what we measure on real maps, indoors and on KITTI
  • Positional noise: Rayleigh perpendicular offsets at the line's own location (7 cm indoor, 28 cm street), never additive Gaussian on m (which would violate the Plücker constraint)
